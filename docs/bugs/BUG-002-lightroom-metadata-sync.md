# BUG-002: Lightroom Metadata Sync Failure

## 1. Symptom
User reports: "I still can't see the changes and classification and sort and improvements we are doing when I open and sync the metadata with lightroom. If this part don't work I can't use this tool."

The user is executing `photohelper develop` (or a pipeline including it) which generates `.xmp` sidecar files containing both standard Lightroom (`crs:`) settings and custom `ph:` namespace settings. However, upon opening Lightroom Classic and explicitly attempting to "Read Metadata from File" to sync, the changes do not reflect in the Lightroom UI (neither standard edit sliders nor custom classifications).

## 2. Technical Context & Hypotheses
Lightroom Classic's sidecar metadata syncing is notoriously brittle. Several potential reasons exist for why Lightroom might silently reject or ignore the XMP files generated by `photohelper`:

1. **Namespace Declarations**: The `.xmp` root node might be missing a necessary XML namespace required by Lightroom for proper parsing (e.g., specific `xmlns:xmp`, `xmlns:crs`, `xmlns:lr`, `xmlns:dc` declarations at the `rdf:RDF` level).
2. **RDF Container Structure**: Lightroom expects certain properties to be enclosed in specific RDF sequence tags (`<rdf:Seq>`, `<rdf:Bag>`, `<rdf:Alt>`). Our writer might be writing flat attributes instead of expected nested nodes (e.g., for hierarchical subjects, keywords, or color labels).
3. **Filename Case Sensitivity**: The generated sidecar might be named `.xmp` instead of `.XMP` (or vice-versa), or missing the base extension if Lightroom treats certain CR3s as needing `.CR3.xmp` instead of just `.xmp`.
4. **File Modification Time (mtime) Conflicts**: We artificially set the physical `mtime` to match `ph:LastProcessedAt`. Lightroom might see this `mtime` as older than its own internal catalog representation, concluding that the file on disk is "stale" and silently skipping the "Read Metadata" operation.
5. **Namespace Isolation (`ph:`)**: As noted in DN-029, the custom `ph:` namespace is ignored by Lightroom UI entirely. If the user expects to see NIMA scores explicitly, we must ensure they are properly mapped to `xmp:Rating` and `lr:hierarchicalSubject` (which we do if `--lr-rating` and `--lr-keywords` are provided). The user might be missing the flags, or the flags might not be writing the valid Lightroom schemas.

## 3. Impact
**CRITICAL.** The tool's primary value proposition as an AI pre-culling proxy for Lightroom is defeated if the resulting data cannot be ingested by Lightroom. This blocks user adoption.

## 4. Remediation Plan
This requires dedicated investigation in a subsequent session.
- **Action**: Schedule a dedicated bug-squashing session (e.g., Session 11) to reverse-engineer Lightroom Classic's exact XMP parsing requirements.
- **Methodology**: Create a sidecar in Lightroom, export it, and byte-for-byte compare its XML schema with `photohelper-sidecar`'s generated XML. Identify the structural difference causing the silent rejection.
- **Temporary Workaround**: Ensure the user is explicitly invoking `--all-lr` to emit `xmp:Rating` and `lr:hierarchicalSubject` which are the only fields Lightroom natively surfaces.

## 5. Resolution (Session 11)
**Status:** FIXED.

The root cause was identified: Lightroom completely ignores `crs:` edits (like exposure, tint, etc.) unless the `<rdf:Description>` node explicitly includes the attribute `crs:HasSettings="True"`.

The fix involved:
1. Emitting `crs:HasSettings="True"` whenever any `crs:` fields are present.
2. During the fix, an 8-agent adversarial audit of `photohelper-sidecar` was conducted, yielding 17 findings (4 CRITICAL, 8 HIGH) including a severe TOCTOU race in file writing, potential XML injection via PID, and test gaps.
3. A "Deep Remediation Blueprint" was drafted and executed to resolve these architectural issues entirely, moving the crate from a naive `.xmp` implementation to a robust, conflict-free, and Lightroom-compatible implementation.
